## 图像增强链路细查（承接上条）

三个图像 tool 各自映射到独立 endpoint + model，但共用同一套 `processImageSync` 骨架：

| tool | endpoint | model | 独有参数 |
|---|---|---|---|
| `enhance_image_sync` | `/image/enhance` | `avc-image-enhance` | `scale`（默认 2，无 min/max 校验） |
| `colorize_image_sync` | `/image/colorize` | `avc-image-colorize` | 无 |
| `denoise_image_sync` | `/image/denoise` | `avc-image-denoise` | 无 |

需要记住的判断：

- 三者共用一个任务查询端点（`GET /api/v3/contents/generations/tasks/{task_id}`），**该端点和视频任务共用**，
  即 task_id 空间是混合的 —— 图像工具与视频工具的状态查询走同一条路。
- README 写"colorize/denoise 参数与 `enhance_image_sync` 相同"**不准确**：`scale` 是 enhance 独有，
  后两者 schema 里没有该字段。若后续要对齐文档，这是要改的一处。
- "人脸优化"只存在于文档措辞里，代码无对应参数或开关，是 `avc-image-enhance` 模型内部行为。
- 无复合能力：一次调用只能选一种 task_type，"先降噪再上色"必须串行调两次。
- `poll_interval` / `timeout` 由模型填写且无上限，stdio 单线程下会占住进程。

重构状态：工作区（未提交）已把三个模块各自的上传实现抽到 `src/upload.ts`，
功能面与 `HEAD`（6c03aa5）完全一致，属纯行为等价重构。

## 视频增强链路细查

3 个 tool：`create_task`（异步，`POST /api/v3/contents/generations/tasks`，model `avc-enhance`）、
`get_task_status`、`enhance_video_sync`（内部建任务 + 轮询，50s 截断）。
参数是 `resolution` **枚举**（480p/540p/720p/1080p/2k），**不是**图像侧的 `scale` 倍数 —— 两侧参数模型不同，
改契约时别想当然对齐。

与图像侧的结构性差异：

- 视频**有**异步 `create_task`，图像没有。原因是视频耗时长，sync 50s 几乎必然截断。
- 视频本地文件与图像共用 `upload.ts` 和**同一个**签名端点
  （`/api/v3/contents/generations/tos-signature`），只有 adapter 的 `fileType` 不同（`video` / `image`）。
- 视频任务与图像任务共用 `GET /api/v3/contents/generations/tasks/{task_id}`，task_id 空间混合。

能力边界（已用 grep 确认 `src/` 内**不存在** audio / fps / frame / interpolat / stabil 任何代码）：

- 视频侧只做**分辨率增强**。没有帧插值、没有稳像、没有音频处理、没有时长或码率参数。
- **100MB 上传上限对视频是硬约束**：`checkLocalFile` 对本地视频同样卡 100MB，
  1080p 素材按常见码率算只够很短一段；长视频实际只能走 URL 直传。这是本地路径的真实适用边界。
- `resolution` 枚举限制了取值范围，但代码不校验"只升不降"，降档行为由上游决定。

重构状态同上：`HEAD` → 工作区为纯行为等价重构，功能面未变。

## 模型可选性核实

问「enhance 模型可以选择吗」→ **不能**。全仓库 `model` 只出现在两处，均为硬编码字面量：

- `src/video-enhancement.ts:160`：`{ model: 'avc-enhance', content: [contentItem], resolution }`
- `src/image-enhancement.ts:166-177`：`getModelByTaskType()` 三个 `return`（`avc-image-enhance` /
  `avc-image-colorize` / `avc-image-denoise`），是模块内私有函数，未导出、不可注入。

四个配置入口全部排查过，**没有**任何 model 相关项：tool schema（无该字段）、env（仅 API_KEY /
HTTP_API_BASE_URL / SAM3_API_BASE_URL / SAM3_POLL_INTERVAL / SAM3_POLL_MAX_ATTEMPTS）、
CLI args、`config.json`（仅 baseUrl / sam3BaseUrl）。两版 README 也从未把 model 作为可配概念。
SAM3 侧 `/predict` payload 只有 `{ file_id, prompt }`，同样无 model。

结论：唯一的"模型选择"维度就是**选 tool**——三个图像 tool 各绑一个模型，视频只有一组 tool。

若将来要开放为可配，三种改法及代价（供决策，尚未实施）：

- A 枚举 tool 参数：`z.enum([...]).default(...)`。LLM 可切，但把上游模型清单硬编码进本项目，上游加模型需发版。
- B env 覆盖：`MODEL_ENHANCE` 之类。不动 tool 契约，但一个进程只能一套模型。
- C 裸字符串透传：`z.string().optional()` 不校验。上游换模型无需改本项目，代价是错误要由上游报（现有
  `[API call failed] status=... data=...` 已能透传上游诊断）。

前置未知项：**上游到底接受哪些 model 名，仓库内无任何线索**，需向上游确认后才能定白名单。
另注：第三方目录站（mcp.film 等）聚合信息里也未提及任何多模型可选，且其版本号已过期
（写 media-mcp 0.2.1，本地实为 0.3.0），不可作为依据。

## 横竖版 / 宽高比核实

问「视频增强能否自动区分横版纵版」→ **不能，项目完全不感知画幅朝向**。

三环证据：

- 入参：只有 `resolution` 枚举（480p/540p/720p/1080p/2k），无 aspect / orientation / 宽高字段。
- 上传：`checkLocalFile` 只 `stat`（存在性 + ≤100MB），**不看内容**；本地视频 `fs.createReadStream`
  流式直传，server 从不解析容器。URL 直传时更极端 —— 只传一个字符串，连字节都不碰。
- payload：`{ model: 'avc-enhance', content: [...], resolution }`，就这三个字段。

全仓库 grep `aspect|orientation|portrait|landscape|width|height|ratio` 无任何真实命中
（仅 `generations` / `declaration` / `operations` 里恰好含 `ratio` 子串的误命中，
以及 README 解释 SAM3 box 坐标的 "Width = x2 - x1" 一段）。

**真正的风险点是 `resolution` 的语义缺口**：480p/720p/1080p 这套命名源自横版 16:9，数字指**高度**。
对竖版（如短剧 9:16）素材，上游按短边=720（→720×1280）还是按高度=720（→405×720）处理，
代码与文档都没定义。这个只能实测。

实测方法（本机 `/opt/homebrew/bin/ffprobe` 可用，工作区无测试素材）：

```bash
ffprobe -v error -select_streams v:0 -show_entries stream=width,height -of csv=p=0 input.mp4
```

取一段竖版素材调 `create_task`（resolution: 1080p），完成后把返回的 `video_url` 下回来再 ffprobe：
输出 1080×1920 → 上游按短边解释，竖版安全；输出 606×1080 之类 → 上游按高度硬套，竖版被缩小。

**该实验尚未执行**（需真实 API_KEY，会消耗额度并产生外部请求，故未擅自发起）。
结论：先实测再决定是否加代码 —— 若上游本就保持宽高比，客户端什么都不用做。
